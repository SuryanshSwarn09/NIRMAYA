# Principal Software Engineering Audit: backend/pytest.ini

## Layer A: Executive TL;DR & Architectural Roster

### Executive Summary
`backend/pytest.ini` defines the global testing configuration for NIRMAYA's backend test suite. It configures test discovery paths (`tests/`), test naming patterns, automated asyncio fixture event loop scoping (`asyncio_mode = auto`, `asyncio_default_fixture_loop_scope = function`), and warning suppression rules. While compact and functional, it unconditionally suppresses all deprecation warnings (`ignore::DeprecationWarning`), masking upcoming breaking changes across core runtime dependencies (such as SQLAlchemy 2.0 / Pydantic v2 / Cryptography / FastAPI). Furthermore, it lacks test category markers and automated code coverage enforcement flags.

## Layer B: Plain-Language Developer Walkthrough

The `backend/pytest.ini` file dictates how pytest identifies and executes unit, integration, and security tests across the backend repository:
1. **Discovery Scope (Lines 2-5)**: Directs the discovery runner to scan the `tests` directory for any Python files matching `test_*.py`, inspecting classes matching `Test*` and functions starting with `test_*`.
2. **Asynchronous Execution (Lines 6-7)**: Sets `asyncio_mode = auto`, allowing async test functions (`async def test_*`) to execute without explicit `@pytest.mark.asyncio` decorators. Scopes default fixture loops to the `function` level to prevent cross-test state leakage.
3. **Warning Filters (Lines 8-9)**: Configures global warning suppression, specifically ignoring all instances of `DeprecationWarning`.

## Layer C: Technical Deep Dive & Invariant Analysis

### Invariant 1: Unconditional Global Deprecation Warning Suppression
In lines 8-9:
```ini
filterwarnings =
    ignore::DeprecationWarning
```
Unconditionally ignoring `DeprecationWarning` prevents engineers from seeing deprecation notices generated by third-party packages. When upgrading major framework versions (e.g., Python 3.12 -> 3.13, Pydantic 2.x, SQLAlchemy 2.0), deprecated patterns that will raise `AttributeError` or `TypeError` in future releases fail to trigger warnings during CI runs. Warnings should be filtered selectively by package regex or escalated to errors (`error::DeprecationWarning:app.*`).

### Invariant 2: Lack of Test Categorization Markers
The configuration does not define custom markers (e.g., `markers = unit, integration, slow, abdm_sandbox, fuzzer`). As a result, running subsets of tests (such as fast unit tests versus slow network-bound ABDM sandbox tests) requires cumbersome directory path parameters rather than standard `-m "not slow"` or `-m "unit"` CLI flags.
