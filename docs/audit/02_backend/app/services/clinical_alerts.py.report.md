## Layer A: Executive TL;DR & Architectural Roster

### System Topology & Interaction Flow
The `clinical_alerts.py` module evaluates inbound laboratory analyte measurements against critical panic thresholds, dispatches real-time WebSocket push notifications to assigned clinicians, and tracks formal clinical acknowledgment workflows.


## Layer B: Plain-Language Developer Walkthrough

1. **Rule Registry**: Maintains standardized panic thresholds for critical analytes using LOINC codes (Potassium `2823-3`, Troponin I `42757-5`, Glucose `2345-7`, Platelets `777-3`, Creatinine `2160-0`, Blood pH `2744-1`, Hemoglobin `718-7`).
2. **Analyte Evaluation**: When a lab result is ingested via `evaluate_lab_observation()`, it resolves the test name/LOINC code and checks if the value breaches panic bounds.
3. **Alert Dispatch**: If panic thresholds are breached, an alert record is created and immediately dispatched via `ws_manager.broadcast_event` across doctor-specific and facility-wide WebSocket channels.
4. **Clinician Acknowledgment**: Clinicians can acknowledge the panic alert via `acknowledge_alert()`, recording timestamp, clinician ID, and clinical action taken.

## Layer C: Technical Deep Dive & Invariant Analysis

### 1. In-Memory Ephemeral Storage vs Medicolegal Audit Invariants
The alert storage is backed entirely by an in-memory dictionary `self._alerts: Dict[str, ClinicalAlertResponse] = {}`. In a production hospital setting, laboratory panic values (e.g. acute myocardial infarction or critical hyperkalemia) require tamper-evident, permanent retention in PostgreSQL. If the Uvicorn process restarts or scales to multiple worker processes, alerts generated by one worker are invisible to doctors connected to another worker, and all historical acknowledgments are lost.

### 2. Unauthenticated Alert Acknowledgment (IDOR / Verification Bypass)
In `acknowledge_alert(alert_id, request)`, the method accepts an `AlertAcknowledgeRequest` containing `doctorId` and `clinicalAction`, and updates the alert without verifying whether the requesting clinician has privileges to acknowledge alerts for that patient or matches the assigned `doctorId`. Furthermore, no database transaction or cryptographic audit hash is committed.

### 3. Concurrency & Performance Scaling
While protected by `threading.Lock()`, methods such as `get_doctor_alerts()` and `get_doctor_stats()` iterate linearly ($O(N)$) across all system alerts across all facilities to filter records for a single doctor. As alerts accumulate over weeks of continuous operation, this will introduce latency spikes on the event loop.
